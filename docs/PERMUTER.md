# VC5 source permuter

tools/permute.py searches ordinary C++ source variants for one function while compiling the whole source file with the compiler, defines, include paths, and flags selected by recon.json. It never changes src/. Variants and compiler workers are isolated below scratch/permute/ and build/permute/.

## Usage

    .\.pyenv\python.exe tools\permute.py --tu src/event.cpp=scratch\candidate\event.cpp --function '?DrawButtons@CEvent@@QAEHXZ' --rva 0x16f70 --budget 80 --jobs 8 --seed 41

--budget counts the baseline compile. The default is 80 attempts and one worker per logical CPU; choose a lower --jobs if disk or memory pressure matters. The function body is found by its decorated name, then only that body is rewritten. Candidate-local quoted headers resolve beside the candidate first. Each attempt has its own object and TMP/TEMP directory under build/permute/<function>/workers/.

The summary records baseline and best scores, compile count, mutation labels, and paths to the source variants. best-NN.diff files are unified diffs against the input candidate. A diff is a proposal for review, not source to accept automatically. Run an apparent strict result through the normal full-TU verifier:

    .\.pyenv\python.exe tools\verify.py --tu src/event.cpp=scratch\permute\<function>\variants\v00001\event.cpp --build-dir permute_review

## Search operators

The current subset proposes adjacent independent assignment swaps; braced if/else inversion; relational operand reversal for bare atoms; adding or removing a typed temporary for a repeated member/local expression; for/while changes; splitting or merging scalar declarations and initialization; arithmetic and bitwise compound assignment expansion/contraction; assignment ternary conversion; small flat switch/if-chain conversion in both directions; integer +/| reassociation; and moving a scalar declaration across one braced if scope.

Parsing is text-based and intentionally conservative. In particular, an operator may skip nested or unfamiliar syntax. A score improvement does not prove semantic equivalence: inspect every diff for data dependencies, scope, volatile access, integer type, and control-flow changes before using it as reconstructed source. The tool does not add padding, unused code, volatile, inline assembly, or generated bytes.

The VC5 catalog marks these rewrite families inert, so they are omitted: !x versus x == 0, postfix versus prefix increment, p[i] versus *(p+i), and local renames. See msvc5kb/README.md and msvc5kb/catalog.json.

**[EVIDENCE]** msvc5kb/tools/kb.py hints returned keyword matches only for all target functions in this validation; it supplied no function-specific rewrite rule.

## Score

tools/asmscore.py uses cmpfunc to parse the COFF object and resolve the candidate at the requested oracle RVA. It compares x86 instruction tuples (mnemonic, registers, memory addressing, immediates, and relocation slots), with internal branch targets made function-relative. difflib.SequenceMatcher aligns the tuples; for streams over 200 instructions it enables autojunk to keep repeated load/store sequences tractable. The exact-match count is the size of those aligned matching blocks, not a proof of a globally optimal edit alignment.

The score is 2 * instruction_edits + size_delta + verification_penalty, where instruction_edits = candidate instruction count + oracle instruction count - 2 * exact aligned instructions, and the penalty is 0 only when cmpfunc reports STRICT, otherwise 1. The oracle span uses the larger of the recorded Ghidra body size and the gap to the next recorded function start, so padding can affect ranking. A score of zero is accepted only with STRICT; the scorer raises if a strict result does not normalize to zero. A byte mismatch short-circuits symbol resolution because cmpfunc cannot classify that candidate as strict.

**[EVIDENCE]** Score zero agreed with strict comparison on accepted CMenu::Delete (0x1f020), CJauge::SetLevel (0x1ef60), CEvent::GetPhase (0x1ae20), and CButton::SetState (0x2ca0). The deliberately corrected Delete candidate and the ChangeButtons baseline were also checked in full-TU verification.

**[EVIDENCE]** An initial NetAdjustLobbyButtons trial incorrectly rewrote part of button < LIMIT + count as LIMIT > button + count and scored 271. The operator now rejects operands embedded in surrounding arithmetic/logical expressions. The corrected 20-compile run stayed at 281; the earlier score is excluded.

## Compiler findings

- **[EVIDENCE] VC5-ORD-01, CEvent::DrawButtons, blupi-specific:** trigger was the pre-fix ordering of independent pos.y and pos.x stores. Under SP3 /O2 /GX /ML /Gd /Gy in the event TU, the single swap changed the score 1097→1085 and prefix 1069→1525, but remained MISMATCH. The permuter recovered the known ordering after 21 variant compiles. This confirms the search can find a real order correction; it does not establish a transferable register-allocation rule.
- **[EVIDENCE] VC5-ORD-01, CMenu::Delete, blupi-specific:** an intentionally swapped independent pair scored 5; the reverse store order scored 0 and was STRICT in full-TU verification (32 bytes). Total compiles: 2. The result validates the adjacent-assignment operator on this function only.
- **[EVIDENCE] VC5-ORD-01, CDecor::MoveObjectDetect, negative for exact matching:** swapping independent rectangle stores reduced score 561→557 but stayed MISMATCH (20 compiles). No match is claimed.
- **[EVIDENCE] VC5-CTX-01..04, negative search result:** ChangeButtons was already STRICT in the baseline event TU; 20 compiles did not improve its 779-instruction body. No rewrite was needed.
- **[EVIDENCE] VC5-CTX-01..04, negative search results:** GetBlupiInfo, ReadConfig, and MoveObjectSort had no score improvement in their bounded runs. This only narrows the tested text rewrite subset; it does not disprove TU-context or source-form causes.
- **[EVIDENCE] VC5-ORD-01, CEvent::NetAdjustLobbyButtons, negative:** a partial-operand comparison rewrite appeared to improve the score but was not equivalent and has been blocked by the operand-boundary guard. The corrected 20-compile search did not beat score 281. No source-form result is claimed.

## Open limits

**[OPEN]** The tool does not prove variants meaning-preserving and its regex operators cover a C++ subset, not arbitrary syntax. **[OPEN]** Instruction alignment on very large repetitive bodies is heuristic. The selected stuck-function runs show that a lower score is not necessarily close to strict; score is a search guide, and verify.py remains the acceptance check.
